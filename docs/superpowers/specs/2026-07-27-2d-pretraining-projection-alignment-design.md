# 2D pretraining with projected articulation alignment

**Date:** 2026-07-27
**Status:** loss + heads implemented and unit-verified; no datamodule yet

Two deviations from the design below, both forced by things found while
implementing:

1. **`OriginDepthHead` predicts absolute metric depth, not a depth-map
   offset.** The depth maps are not on a common scale: `scenefun3d.py:133`
   divides by 1000 so SF3D arrives in **metres**, while `opdreal.py:211` does
   not so OPD arrives in **millimetres** (verified: float32, nonzero values
   ~152/1123/3135). Referencing the depth map would bake that 1000x
   inconsistency into a metric head. Absolute metres is supervised
   unambiguously by `motion_origin_3d[2]`. Recorded in
   `knowledge/dataset-notes.md`.
2. **`unpack_batch` also accepts a dict batch.** A positional tuple encodes its
   dataset in its length, which does not extend to a 2D source without
   inventing a layout for a datamodule that does not exist yet. Dict batches
   are named, so a 2D source supplies exactly the fields it has and everything
   else is `None`.

## Goal

Enable large-scale pretraining on mined 2D video data (egocentric hand tracks),
such that the **3D articulation head** transfers to 3D finetuning on SF3D/OPD.

Two stages:

1. **2D pretraining.** No 3D ground truth. Train the trunk, a new 2D
   hand-trajectory head, and the 3D articulation head — the latter supervised
   *only* through how it projects into the image.
2. **3D finetuning.** Existing SF3D/OPD supervision, warm-started from stage 1.

The articulation the model learns in stage 1 will be right in-image and
arbitrary in depth. That is expected and is a hard limit, not a tuning problem.

## The central problem, and why it is smaller than it looks

The mined 2D trajectory is the **hand's** path. The SF3D trajectory is *"the
path swept by the functional element"* (`tools/sf3d_process.py` docstring).
Those are different curves — hands approach, slip and retract — and
`knowledge/summary_paws.md` already flags the mismatch.

But for a rigid body on a 1-DOF joint, take any point `p₀`:

```
revolute:   d(θ) = [R(n,θ) − I](p₀ − c)   ⟹   n · d = 0   for every p₀
prismatic:  d    = λ·n                      ⟹   d ∥ n     for every p₀
```

`R(n,θ)` preserves the component along `n`, so the perpendicularity holds
regardless of which point is tracked. **The geometric constraint is invariant
to the choice of body point.** A hand gripping a door and the door's centroid
trace different arcs — different radius, different plane offset — but both are
generated by the same `{type, axis, origin}`.

So the split is:

| quantity | hand vs element | transfers? |
|---|---|---|
| `{type, axis, origin}` | **identical** | ✅ |
| trajectory values | different curves | ❌ |

The design follows directly: **align on the articulation, never on the
trajectory.** Trajectory-to-trajectory matching would reintroduce the mismatch;
articulation alignment is immune to it.

## What is observable in 2D

Projection destroys exactly one degree of freedom. Stage 1 can teach the two
in-plane DOF of the axis and (via arc curvature) the in-plane origin. It can
teach **nothing** about depth. Stage 2 therefore only has to learn depth, not
the whole articulation.

Note the asymmetry that follows from this, since it drives the loss design:

- **Prismatic projects exactly.** `d = λn ⟹ d_proj = λ·n_proj`. A 3D line
  projects to a 2D line.
- **Revolute does not.** `d·n = 0` becomes `d_proj·n_proj = −d_z·n_z` in
  projection — the correction term is precisely the depth component that is
  unobservable. Perpendicularity is only recoverable when the axis lies
  parallel to the image plane.

This is why the loss cannot be the 2D analogue of the shipped `pred_pred`
term. It has to be a reprojection residual instead.

## The loss: forward-project, do not fit

**Rejected alternative:** fit a line/ellipse to the observed track and compare
its parameters to the predicted axis. Ellipse fitting from ~20 noisy points
over a short arc is ill-conditioned exactly where the data lives (a cabinet
opened 30°), and a bad fit feeds a *wrong* gradient rather than a weak one.

**Chosen:** the articulation defines a curve; measure how far the observed
points fall from it.

```
  predicted {type, axis n, origin c}
              +
  hand's own observed start p₀, lifted to 3D   ──►  1-parameter 3D curve
              │
              ▼
        project with K   ──►   curve in the image
              │
              ▼
  L = mean image-space distance from each observed hand point to that curve
```

Two properties make this work:

- **Anchoring at the hand's own start** means the radius is automatically the
  hand's radius. The element's reference point is never needed — this is where
  body-point invariance is cashed in.
- **The curve parameter is free per point** (`sᵢ` for prismatic, `θᵢ` for
  revolute), so phase and speed are unconstrained. A hand that pauses or moves
  unevenly costs nothing. Only *lying on the curve* is required.

A short, low-curvature arc yields a **weak** gradient rather than a wrong one,
which is the correct failure mode.

### Prismatic branch — closed form

A 3D line projects to a 2D line, so no search is needed. The image line passes
through `p₀` and the vanishing point `π(K·n)`:

```
L_line = mean_i  dist( pᵢ , line through p₀ and π(K·n) )
```

### Revolute branch — sampled

`P(θ) = c + R(n,θ)(P₀ − c)` projects to a conic; point-to-conic distance has no
convenient closed form. Sample `θ` on a fixed grid (M = 64) over a plausible
sweep, project, and take the distance to the resulting polyline:

```
L_arc = mean_i  min_m ‖ π(K·P(θ_m)) − pᵢ ‖
```

Cheap (`N×M` with N=20, M=64), differentiable, and robust. Use a soft-min if
the hard `min` proves jumpy in practice.

### Anchor depths

Two scalars are needed to place the curve in metric 3D:

| symbol | meaning | source |
|---|---|---|
| `Z₀` | depth of the hand's start | read from the depth input at `p₀` |
| `Z_c` | depth of the joint origin | depth at `coords_hat` **+ predicted offset** |

`Z₀` needs no head. `Z_c` is a small **offset** head rather than an absolute
depth predictor — better conditioned, and it lets the hinge sit behind the
visible surface (a hinge inside a cabinet). The 3D origin is then

```
c₃D = Z_c · K⁻¹ · [u, v, 1]          (u,v) = coords_hat
```

This closes a real gap: **the model has never predicted a 3D origin at all**
(`motion_origin_3d` is GT-only, which is why the shipped `cross_gt` loss
teacher-forces it). In stage 2 the offset head is supervised directly against
`motion_origin_3d`.

It also means the existing interaction-point head is supervised *indirectly*
in stage 1 — the residual backprops through `coords_hat` — and on the **correct**
target, the hinge, because arc curvature is what localises a rotation centre.
No separate contact-point head is required: the loss anchors on the observed
hand start from ground truth, not a prediction.

Normalise residuals by the image diagonal to keep the loss dimensionless and
comparable to the other O(1) terms.

## Motion type: a soft gate that must pay for itself

The mined data carries **no motion-type label**, so the branch must be gated on
the model's own prediction. That is dangerous in a specific, structural way.

**A line is a circle of infinite radius**, so the revolute hypothesis class
*contains* the prismatic one:

```
min residual over revolute params  ≤  min residual over prismatic params   (always)
```

Written softly, the gradient on `p` is non-positive everywhere:

```
L = (1−p)·L_line + p·L_arc      ⟹      ∂L/∂p = L_arc − L_line ≤ 0
```

This is not a tendency, it is structural: an unpenalised gate collapses to
revolute. This is the *opposite* direction from the gate-cheating risk in the
`pred_pred` loss, where the two branches were exact complements and neither was
intrinsically cheaper.

The fix is standard model selection — make the richer hypothesis pay:

```
L_proj = (1−p)·L_line + p·(L_arc + λ·R_radius)
⟹ ∂L_proj/∂p = (L_arc + λ·R_radius) − L_line
```

`p` now rises only when the arc's residual advantage **exceeds** its complexity
cost. `R_radius` penalises `r = ‖(P₀ − c)⊥n‖`, which is metric because
intrinsics are known, and physically bounded (a door is ~0.4–0.9 m). Use a
smooth hinge above a reference radius rather than a clamp, so gradients
survive. This is literally "don't explain a straight line by putting the hinge
50 m away."

Add a weak prior term on `mean(p)` anchored to the prismatic/revolute balance
measurable in OPD, purely to stop early collapse.

**What the bias actually costs:** the mislabelled type is the lesser damage —
`knowledge/training-findings.md` records type as ~97–100% accurate and solved
by epoch 1, so stage 2 re-fixes it almost immediately. The real cost is that an
unpenalised revolute branch drags the **origin and depth-offset heads** toward
absurd geometry, and those are exactly the components that are new, have no
other supervision in stage 1, and most need pretraining. The complexity penalty
protects the origin head, not the type head.

## Architecture changes

Following the existing flag pattern (`use_depth`, `use_cvae` in `ModelParams`):

```python
use_trajectory_head: bool = True      # False in stage 1
use_2d_trajectory_head: bool = False  # True in stage 1
predict_origin_depth: bool = False    # True in both, once available
```

**New heads**

- `Trajectory2DMLP` — `(B, N, 2)`, mirroring `TrajectoryMLP` including its
  relative-to-own-first-point convention (no separate anchor head, and the GT
  track is made relative the same way). Direct 2D GT supervision; this is the
  dense signal that makes large-scale pretraining worth doing.
- `OriginDepthHead` — one scalar offset, as above.

**`ModelOutputs`** gains `trajectory_2d_pred` and `origin_depth`, both
`Optional`. **`StepTargets`** gains `trajectory_2d`; `camera_intrinsic` already
exists and is currently unused by any loss.

**Loss registry** gains a variant, fitting the interface unchanged:

```
geometric_loss: "cross_gt" | "pred_pred" | "projected" | "none"
```

`TrajectoryMLP` is a clean leaf — nothing consumes its output and
`vae_condition_dim` is computed independently — so `use_trajectory_head: false`
removes it safely. `load_finetune_weights` (`train_OPDReal_better.py:958`)
already filters to keys present in both checkpoint and model, so a stage-1
checkpoint lacking `trajectory_predictor.*` loads into the stage-2 model with
the head freshly initialised and reported in `unloaded_keys`.

### Head inventory by stage

| head | stage 1 | stage 2 | transfers |
|---|---|---|---|
| mask | direct GT | direct GT | ✅ |
| articulation (axis + type) | **indirect** via projection | direct 3D GT | ✅ |
| origin depth offset *(new)* | implicit in projection | vs `motion_origin_3d` | ✅ |
| interaction point (existing) | **indirect** via projection | direct GT | ✅ |
| 2D hand-trajectory *(new)* | direct 2D GT | idle / frozen anchor | — |
| `TrajectoryMLP` | **removed** | direct GT | n/a |

## Depth input: assumed present in both stages

**Decided (2026-07-27):** stage 1 runs with `use_depth: true`, most likely fed
by a monocular depth estimator. Sourcing that is deferred.

This matters because `use_depth` is architectural, not a loss switch — it adds
a `DepthEncoder` and concatenates channels into the FPN, so a stage that ran
without depth would have a different trunk shape and its weights would not
transfer. Keeping it on in both stages makes the architecture identical across
the transfer and supplies the `Z₀` anchor for free.

The cost carried forward: pseudo-depth error propagates into `Z₀`, and hence
into the metric radius the complexity penalty is computed from.

## Risks

- **Depth collapse — the risk most likely to make stage 1 harmful.**
  Many different 3D axes project identically: a hinge tilted slightly toward
  the camera and one tilted slightly away give the same line in the image. The
  loss only sees the image, so the axis's depth component receives no gradient.
  An unconstrained parameter does not stay random — with nothing pushing it and
  weight decay pulling it to zero, it settles at zero, and the model learns
  "every articulation is flat, parallel to the image plane."

  Stage 2 then inherits not ignorance about depth but a *confident wrong
  answer*, and un-learning a committed belief can be worse than starting fresh.

  Mitigation to evaluate: have `MotionVAE` emit several candidate axes per
  image (prior sampling, which it already supports) and require only that
  **one** of them projects correctly — a best-of-K residual. The model then
  preserves the ambiguity instead of resolving it wrongly, and stage 2, which
  does see real 3D, picks the right candidate. Untested; this is why it is a
  risk rather than part of the design.
- **Contact-phase segmentation.** Reach and retract are *not* generated by the
  joint and would violate the constraint outright. PAWS uses a contact detector
  for this; stage 1 depends on that step being reliable.
- **Non-rigid contact.** Hand slip and finger deformation add noise to the
  assumption that the hand moves with the body. Mostly unbiased, but real.
- **Pseudo-depth error** propagates into `Z₀` and hence into the metric radius
  used by the complexity penalty.

## Verification

Unit-testable on synthetic geometry with no data or GPU, in the style of
`tests/test_geometric_losses.py`:

- Exact 3D circle projected with a known `K`; feeding the true articulation
  gives `L_arc ≈ 0`. Same for a line and `L_line`.
- Perturbing the axis raises the residual monotonically.
- **Containment test (the important one):** on a perfectly straight track, the
  best-fitting large-radius arc must score *worse* than the line once
  `λ·R_radius` is applied — i.e. the complexity penalty actually neutralises
  `∂L/∂p ≤ 0`. Without this test the gate bias is invisible until training.
- Phase invariance: reordering or non-uniformly resampling the observed points
  along the same curve leaves the loss unchanged.
- Body-point invariance: two tracks at different radii about the same axis both
  score ≈ 0 for that axis.
- Degenerate: a stationary hand is masked out, not scored.
- `tools/smoke_losses.py` extended with the `projected` variant.

## Non-goals

- **The mining pipeline itself** (tracking, contact detection, hand
  reconstruction). This spec assumes tracks arrive as `(B, N, 2)` plus `K`.
- **Stage-2 changes** beyond loading a stage-1 checkpoint and supervising the
  new origin head.
- **Keeping the 2D head active in stage 2** as an anti-drift anchor — a later
  ablation, not part of the first implementation.

## Note on evaluation timing

There is no SF3D row in `experiments/INDEX.md` yet, so stage 2 currently has no
baseline to measure a stage-1 → stage-2 result against.

This does **not** block implementation — the work here is unit-testable on
synthetic geometry with no data at all, and the heads are not expected to be
trained for some time. It only becomes a prerequisite at the point of claiming
that pretraining helps. `config/sf3d_train_runpod_geo_crossgt.yaml` is the run
that establishes it, whenever that happens.
