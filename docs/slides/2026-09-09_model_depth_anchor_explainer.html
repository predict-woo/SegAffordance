Model structure, depth, and the anchor

What the network computes, where the input depth map is used, and why a missing depth map removes the trajectory supervision.

2026-09-09 · code as of commit 5584f92 · files: model/segmenter.py, model/losses/geometric.py (TrajectoryProjectionLoss), train_OPDReal_better.py (z_p tether)

1The network, end to end

The model takes an RGB image, a depth map and a text description, and predicts four things about the described part: its mask, its interaction point, its articulation (type, axis, origin), and a trajectory of the interaction point. Depth enters exactly once, in the box drawn orange.

Figure 1. Forward pass. Depth features are concatenated into the two finest FPN levels; everything downstream sees a mixed RGB+depth feature map, never the raw depth again.

The trajectory head outputs offsets: point 0 is always (0,0,0) and the other points say how far the interaction point moves, in metres, in camera coordinates. Where that curve actually sits in 3D is not part of the prediction. That missing starting position is what the code calls the anchor.

2How the 2D recipe supervises the 3D trajectory

HOI4D, EPIC and ARCTIC provide a 2D hand track in pixels, not a 3D curve. The loss therefore has to compare a 3D prediction with a 2D observation, and it does that by projecting the prediction into the image. But a relative curve cannot be projected: to project a 3D point you need its absolute position, so the loss first has to place the curve somewhere.

Figure 2. The projection loss. The pixel position of the anchor is known from the data (the first track point). Its depth is not in the 2D data, so the code reads it out of the input depth map.

3Why the anchor's depth matters so much

Perspective projection collapses scale: a 10 cm motion at half a metre and a 20 cm motion at one metre draw the same 2D track. So the anchor's depth is what tells the network how big, in metres, its predicted offsets have to be. Without it the loss can only teach the shape of the curve, not its size, and the metric trajectory that SF3D later needs is undefined.

Figure 3. Scale ambiguity of a 2D track. The anchor depth z fixes which of the red curves the prediction is compared against, and therefore what "correct" offsets are in metres.

The same depth sample feeds a second term.

The z_p head predicts the metric depth of the interaction point, so the model can lift its own 2D point to 3D at test time. On the 2D recipe nothing supervises z_p directly, so a tether loss pulls z_p towards the input depth map sampled at the same first track point (depth_anchor_weight). That tether goes silent in exactly the same situations as the projection loss.

Figure 4. The 2D track starts at the hand's middle knuckle. On ARCTIC the object is rendered but the hand is not, so the knuckle usually lands on a zero pixel even though the object is right there. On EPIC there is nothing to sample.

So the symptom of "no depth" is not a crash and not a bad number. Training runs, the mask and heatmap losses work normally, and the trajectory head quietly receives no gradient from 80% of ARCTIC and 100% of EPIC. The DepthEncoder itself also sees a map it has never seen in training (all zeros), but that is the smaller of the two problems.

In one sentence: the input depth map is used both as a feature and as the single number that turns a pixel-space track into a metre-space target; making depth optional means giving the network a way to say "absent" for the first role and a fallback source of that one number for the second.

Numbers measured 2026-09-09 on the pod: ARCTIC median GT z at the first point 0.53 m (map agrees where valid, 0.51 m); EPIC WiLoR z median 0.70 m, 278 grip / 81 rotation-only records.
