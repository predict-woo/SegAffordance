The depth map as an input feature

The second, independent place depth is used: not in any loss, but as something the network looks at. What it sees today, why "no depth" is a problem there too, and the three ways to handle it.

1What the encoder does with the depth map

The depth map is a 512×512 image of metres. A small stack of four convolutions (about 0.5 M parameters, next to the frozen 300 M backbone) turns it into two feature maps, and those are glued channel-wise onto the backbone's RGB features before the FPN. From that point on there is no "depth" and no "RGB" any more, only a mixed feature map that the decoder, the mask, the heatmap and every head read.

Figure 1. The fusion point. The FPN's first convolutions were built and trained for 640- and 1280-channel inputs, which is why the depth branch cannot simply be unplugged from an existing checkpoint.

Figure 2. The encoder was trained on the left kind of map. The other two are inputs it has never been shown; the network does not know that "black" means "unknown" rather than "zero metres away".

This is why the loss fix alone is not enough. Even with a scale-free 2D loss that never reads the depth map, the forward pass still pushes the EPIC and ARCTIC maps through the encoder, and the features it produces from a black image are noise the decoder has been trained to trust. The best case is that the network learns to ignore them on those datasets; the likely case is degraded masks and heatmaps, and a model that behaves differently with and without depth without anyone having decided that.

3Three ways to handle the input side

Option A: modality dropout (recommended). Keep the encoder. Give it a second input channel that is 1 where the depth is valid and 0 where it is not, so "absent" is an explicit signal instead of a suspicious reading. Then, during training on the datasets that have depth, blank the whole map for a random fraction of samples (say a third). The network is forced to solve the task both ways and learns what to do when the validity channel is all zero.

Checkpoint compatibility. The only weight whose shape changes is the encoder's first convolution, 1 input channel becoming 2. Pad it with a zero-initialised second channel and every existing checkpoint loads and behaves exactly as before on the first step. The record recipe survives.

Cost. One fine-tune of the record checkpoint with dropout on. It also produces, for free, the first measurement of how much depth is worth: evaluate SF3D with the real maps, then again with blanked maps, and the gap is the price of missing depth.

Option B: an RGB-only model. Set the existing use_depth: false flag. The encoder disappears and the FPN's first convolutions are rebuilt for 512 and 1024 input channels. Cleanest possible model, and no dataset is ever out of distribution.

Cost. Those FPN convolutions cannot be loaded from any existing checkpoint, so the chain that produced the record, HOI4D pretraining then SF3D post-training, has to be rerun from scratch under this flag. This is the proper depth ablation, and nobody has run it yet, so it is worth doing once regardless. It just should not be the thing that gates EPIC and ARCTIC training.

Option C: estimate the depth. Run a monocular metric depth estimator on the EPIC onset frames, and composite ARCTIC's rendered object onto an estimated background. The model stays exactly as it is.

Cost. A permanent domain gap between estimated and sensor depth, a new preprocessing dependency on every future dataset, and the model still cannot be run on a bare RGB image at test time. Useful as a fallback experiment, not as the design.
