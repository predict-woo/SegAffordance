SF3D data filtering: how 458k records became the 59k standing split

Four filters, each added for a measured reason, define the split every generation since gen-9 trains on (g9 … g17-2d). Two remove unsupervisable labels (occlusion, knob-radius ambiguity); two remove targets the model physically cannot resolve at input resolution (sub-pixel masks, border-clipped points). This page records the numbers behind each cut and the cutoff-vs-data trade-off curve.

SF3D annotates the functional element (handle, knob, button), not the object — so most GT masks are a few pixels. No mask head learns a 5×5-px target at 256²; and a 2-cm knob supervises rotation magnitude through pure ambiguity (gen-4: predicted |ω| 0.06 on knobs vs 0.25 on doors, correlation 0.58 with radius).

3 · Choosing the mask cutoff: the data-vs-resolvability curve

Full-DB scan (458k records, after sensor + radius filters). The distribution's knee (p50 0.030%, p75 0.068%, p90 0.157%) sits exactly in the useful cutoff range, so the data cost rises steeply between 0.01% and 0.25%. Source: viz/20260815_sf3d_mask_cutoff_curve/.

Gen-8 probed the aggressive 0.25% end (19.3k records, 4.2% of the full DB). Relaxing to 0.10% tripled the data while still dropping the unresolvable sub-0.1% mass; that compromise became the standing split.

4 · What the close-up probe proved (gen-8, 08-14)

Masks work when targets are resolvable
  • mIoU 0.178, PDet 9.4 — ~1.8× the best any full-split arm reached (g4: 0.118 / 5.6)
  • Same model, same losses, same frozen CLIP — only the data changed
  • traj_dir 94.8% / cos 0.783 (best ever at the time) — clean curves, no zigzag
The reframe

Frozen CLIP was not the binding constraint on masks — target size was. On the full split the median element is ~5×5 px at 256²: "no head fixes that, resolution or cropping does." The mask problem moved from architecture to data/resolution.

Validated twice downstream
  • g9 (0.1% split): 3.1× the data → type 92.0 → 95.0, axis-all 32.8° → 27.6° — volume feeds the semantic heads
  • g13 (512 px input): the resolution half of the same diagnosis — mIoU 0.2655 (+66%), PDet 21.4 (4.2×), both project records

Read with two caveats. (1) Each column evaluates on its own filtered split — these are different denominators, not one benchmark: the mask/3D-localization gains show the task becoming learnable when targets are resolvable, while the type/axis dips show the close-up mix trading away g7's easy full-split classification samples. (2) † g8 also switched the trajectory head from g7's absolute readout back to relative direct, so the traj_dir row mixes the data change with that fix — the split is not its cause. Net: everything the filter was aimed at (masks 2.1×, PDet 3.1×, 3D point −36%, origin −47%, radius −54%) moved, at a measured cost in type/axis on the harder close-up mix.

Accepted costs, on record: each filter narrows the task scope — no knob/dial/faucet rotations, no tiny or border elements; eval splits are filtered identically, so post-filter metrics overstate performance on raw SF3D. The 0.1–0.25% mask band remains hard at 256² (g9's mIoU 0.146 sits between g8's 0.178 and the full-split ~0.10) — that band is what the 512-px stack (g13+) was built for.
