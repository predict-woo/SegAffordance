Backbones: CLIP RN50 vs DINOv3 (dino.txt)

Your understanding is right for CLIP: the backbone hands three feature levels + text features to the shared neck (FPN gated by the text state), then decoder → projector. The DINOv3 backbone slots into the SAME downstream — the interesting part is how it manufactures the three levels and the text alignment that CLIP gets natively. Everything below build_backbone is byte-identical between the two.

1 · Side by side

CLIP RN50 — backbone: "clip_rn50"
DINOv3 ViT-L/16 + dino.txt — backbone: "dinov3"
The structural trick to notice: CLIP RN50 gives the neck raw conv features at /8 and /16 but a text-aligned attnpool map at /32 — and the FPN's gating plus the dynamic kernel rely on that deepest level sharing a space with the text state. The DINOv3 adapter reproduces exactly that split: /8 and /16 are built from the RAW backbone tokens, while the /32 level is built from the aligned dino.txt head tokens (x_deep in SimpleFeaturePyramid.forward, deep_proj 1×1 first). Without that, the text gate would be comparing vectors from two unrelated spaces.

Empirical history (gen-3 head-to-head, viz/20260805_sf3d_g3_clip_vs_dinov3): DINOv3 won geometry (axis/trajectory), CLIP won masks. That was pre-split-heads, pre-heatmap-lift, pre-consistency-loss — the geometry advantage is exactly where the current recipe now concentrates its supervision, which is the case for retesting it as a gen-12 candidate (dinov3 + v3 dataset + rebalanced trajectory weight).

3 · Where it plugs in

build_backbone(model_params, fpn_in) (model/backbones/__init__.py) is the only entry point — selection via ModelParams.backbone. The segmenter consumes the uniform interface (encode_image → 3 maps, encode_text → word, state, tokenize, word_dim/state_dim) and everything downstream — FPN, decoder, projector, all gen-6…11 heads, all losses — is backbone-agnostic. An existing config pair (*_dinov3.yaml, twist-era) already carries the weight paths; a gen-12 config would graft those backbone lines onto the g11b recipe.
